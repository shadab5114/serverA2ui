01 — Overall architecture

Four layers and one turn

Each layer answers a different question: what the user sees, how it travels, who decides, and what constrains the decision. State cuts across all four. If a new feature doesn’t sit in exactly one layer, it isn’t scoped yet.

02 — Where your team’s work lands

One catalog, three jobs

This is the impact argument in one picture. The artifact your team already maintains feeds three different parts of the system — so a component change propagates to all three at once, instead of being re-implemented three times.

03 — User flow

Two personas, the same rails

The customer flow and the designer flow run on identical protocol, validator and renderer. Only two things differ: which graph handles the turn, and how deeply it grounds before it draws.

Both flows move along one dial — how much the agent decides:

Pinnedagent fills a curated template
Composedagent picks a known pattern, fills it live
Generatedagent composes freely from the catalog

What the audience should actually watch

A demo where UI simply appears is indistinguishable from a designer with a good prompt. The thing worth pointing at is the trace panel — the agent consulting your guidelines, citing your rules, and being corrected by your validator.

That is why TOOL_CALL_* is a first-class event in the protocol rather than a debug log, and why every grounding tool returns { answer, sources[] }. Observability of the grounding step is an architecture decision, not a UI one.
