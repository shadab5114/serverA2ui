# Making a Design System A2UI‑Interactive

How we taught a design system to render **dynamic** A2UI — opening modals, submitting & validating forms, navigation, two‑way‑bound inputs — and how to replicate it on **any** design system.

> **Audience:** DS maintainers and app/renderer devs.
> **Scope:** two independent surfaces of work —
> 1. **Catalog (schema) side** — lives in the design‑system repo (here: `D:\DesignSystem\pds`, generated by `scripts/generate-catalog.mjs`).
> 2. **Renderer side** — lives in the app that renders A2UI (here: `ServerSetupA2UI/client`, `src/pdsCatalog.tsx` + `src/App.tsx`).
>
> They are decoupled: the catalog says what an agent may *emit*; the renderer makes it *run*. You can ship the catalog changes and the renderer changes independently.

---

## 1. TL;DR — what this unlocks

Before: the generator could only produce **static** UIs. Components had no way to declare interactions, form inputs couldn't feed data back, and clicking did nothing.

After, an agent can emit — and the renderer executes — A2UI like this:

```jsonc
// a button that submits a form to the agent, gated by validation
{ "id": "submit", "component": "Button", "children": "Sign in",
  "checks": [ { "condition": { "path": "/form/emailValid" }, "message": "Enter a valid email" } ],
  "action": { "event": { "name": "submit_login",
              "context": { "email": { "path": "/form/email" } } } } }

// a link that opens a URL locally (no server round‑trip)
{ "id": "help", "component": "TextLink", "children": "Help",
  "action": { "functionCall": { "call": "openUrl", "args": { "url": "https://…" } } } }

// a modal whose open state is driven from the data model
{ "id": "m", "component": "Modal", "opened": { "path": "/ui/open" },
  "onClose": { "functionCall": { "call": "setData", "args": { "path": "/ui/open", "value": false } } },
  "children": "modalBody" }
```

## 2. Background: the A2UI interaction model

Everything rests on four A2UI concepts. (Spec: <https://a2ui.org/concepts/actions/> and `specification/v0_9/json/common_types.json`.)

| Concept | What it is | Where it runs |
|---|---|---|
| **Event action** | `{ "event": { "name", "context" } }` — a named signal dispatched to the **agent**. `context` values are literals or `{ "path" }` bindings resolved from the data model. | Agent (network round‑trip; agent replies with more A2UI) |
| **Function action** | `{ "functionCall": { "call", "args" } }` — invokes a named function on the **renderer**. | Renderer (instant, local) |
| **Checks** | `checks: [{ condition, message }]` — client‑side validation gates. **A sibling of `action` on the component**, *not* nested inside it. | Renderer (before the action fires) |
| **Data model + binding** | A per‑surface JSON tree. Any value can be `{ "path": "/json/pointer" }`. Inputs write back to it; events/checks read from it. | Renderer state |

**The one rule to teach app teams:** *Does resolving this need the agent (intelligence / server / persistence)? → **event**. Is it pure UI mechanics the renderer can do now (navigate, open a modal, toggle)? → **functionCall**.*

## 3. Part A — Catalog (schema) side

Goal: make the interaction vocabulary a **first‑class, valid** part of every component's schema, and make the catalog **self‑contained** so an LLM (and any JSON‑Schema validator) has the real type shapes — not a URL it can't resolve.

All of this is done centrally in the catalog generator (`generate-catalog.mjs`) so **no per‑component source changes** are needed. Six changes:

### A1. Add an `action` slot to every interactive component

Add an `action` property (referencing the A2UI `Action` type) to the shared base every component spreads (`CatalogComponentCommon`), so it's inherited everywhere.

```js
// in the shared $def every component references via allOf
action: {
  $ref: "#/$defs/Action",
  description: "Interaction fired when the user activates this component: an " +
    "`event` (→ agent) or a `functionCall` (→ renderer, e.g. openUrl/setData). " +
    "Gate it with the sibling `checks`. Only interactive components honour it.",
}
```

**Why the shared base and not per‑component?** Every generated component ends with **`"unevaluatedProperties": false`**. That means a property the schema doesn't declare is **rejected** — an agent emitting `"action": …` on an undeclared component produces *invalid* JSON. Declaring `action` on `CatalogComponentCommon` (which every component pulls in via `allOf`) makes it evaluated — and therefore allowed — everywhere, in one line. (`unevaluatedProperties` sees properties contributed by `allOf`/`$ref` subschemas.)

> **Gotcha #1 — `unevaluatedProperties: false`.** If your DS catalog uses it (recommended for strictness), you *must* declare `action`/`checks` in a schema the component actually references, or they'll be stripped/invalid.

### A2. Make controlled‑state props **bindable** (two‑way)

Form controls expose their state as a plain scalar (`value: string`, `checked: boolean`, `opened: boolean`). A `{ "path" }` binding on a `boolean`/`string`‑typed prop is **invalid** under strict schemas. Convert these state props to the A2UI **`Dynamic*`** union (literal **or** binding):

```js
// prop name → the Dynamic* type by the prop's declared scalar type
const DYNAMIC_STATE_PROPS = new Set(["value", "checked", "opened"]);
const dynamicRef = (t) =>
  t === "boolean" ? "DynamicBoolean" :
  t === "number"  ? "DynamicNumber"  :
  t === "string"  ? "DynamicString"  : "DynamicValue";
// e.g. InputField.value → { $ref: "#/$defs/DynamicString" }
//      Checkbox.checked → { $ref: "#/$defs/DynamicBoolean" }
//      Modal.opened     → { $ref: "#/$defs/DynamicBoolean" }
```

**Why only these props, and not `default*`?** `value`/`checked`/`opened` are the *controlled* state the UI reads and writes. `defaultValue`/`defaultChecked` are initial seeds — those stay literal; seed initial state via an `updateDataModel` message instead of binding a default.

### A3. Turn close handlers into actions

`Modal.onClose` / `Notification.onClose` were opaque `{ "type": "object" }` — the agent couldn't fill them in, and `Modal.onClose` was **required**, so the agent literally could not emit a valid Modal. Convert them to `Action` and drop from `required`:

```js
const ACTION_HANDLER_PROPS = new Set(["onClose"]); // → { $ref: "#/$defs/Action" }
// and: exclude these from the component's `required` list
```

### A4. Give nested clickable items their own `action`

Items that render as their own clickable element but **don't** inherit `CatalogComponentCommon` (e.g. `ButtonGroupItem` — the buttons in a ButtonGroup and in a Modal footer) need `action` injected explicitly:

```js
const ACTIONABLE_DEFS = new Set(["ButtonGroupItem"]);
// inject `action` into each oneOf variant of these shared $defs
```

> **Gotcha #2 — nested items.** `action` on the base only covers top‑level components. Your primary CTA path (button groups, modal footers) often runs through a *nested* schema that doesn't inherit the base. Miss this and those buttons can't do anything.

### A5. Add `checks` as a **sibling** of `action`

Reading the real spec corrected a common misconception: **`Action` has no `checks`.** Validation comes from the separate `Checkable` mixin, so `checks` sits *next to* `action` on the component, not inside it. Add a `checks` array (of `CheckRule`) to the shared base:

```js
checks: {
  type: "array",
  items: { $ref: "#/$defs/CheckRule" },
  description: "Client‑side validation evaluated before this component's `action` " +
    "fires. Each { condition, message } blocks the action while its condition is false. " +
    "A sibling of `action`.",
}
```

> **Gotcha #3 — `checks` placement.** `{ action: { checks: [...] } }` is **wrong** and will not validate. It is `{ checks: [...], action: {...} }`.

### A6. Vendor the A2UI common types → self‑contained `$defs`

The refs above (`Action`, `Dynamic*`, `CheckRule`, `DataBinding`, …) point at the **external** A2UI spec (`https://a2ui.org/…/common_types.json#/$defs/Action`). An LLM doesn't dereference URLs, and your catalog‑serving layer likely doesn't inline them — so the shapes are **missing** at the point of use. Fix: **vendor** the spec's `$defs` into the catalog's own `$defs` and make all refs **local**.

```js
// vendored once from the spec: scripts/a2ui-common-types.json
const A2UI_COMMON = "#/$defs";                       // was the spec URL
const A2UI_COMMON_DEFS = (() => {
  const defs = JSON.parse(readFileSync("scripts/a2ui-common-types.json","utf8")).$defs;
  delete defs.FunctionCall.oneOf;                    // strips a cross‑file `anyFunction` ref
  return defs;
})();
// …then spread A2UI_COMMON_DEFS into the emitted catalog.$defs
```

**Why this matters even though it "worked" before:** `DynamicString` was already referenced externally and rendering was fine — because the *prompt* explained bindings verbally. But actions are richer (event vs function vs checks), and no amount of prose substitutes for the shape being present. Vendoring makes the catalog **portable and validator‑correct**: fetch any single component and you get `Action`, `FunctionCall`, `DynamicValue`, `DataBinding`, `CheckRule`, … bundled with it.

> **Gotcha #4 — the spec's own dangling ref.** `FunctionCall` in the spec has `oneOf: [{ $ref: "catalog.json#/$defs/anyFunction" }]` — a hook for a catalog to *whitelist* its function names. If you don't define `anyFunction`, strip that `oneOf` (as above) or every `FunctionCall` dangles. **Future win:** define `$defs/anyFunction` listing your renderer's functions (`openUrl`, `setData`, …) to make the schema itself reject unknown `call` names.

### Catalog side — verification

After regenerating, assert the catalog is self‑contained:

```js
const txt = fs.readFileSync("catalog.json","utf8");
assert((txt.match(/a2ui\.org/g)||[]).length === 0);        // no external refs
assert((txt.match(/anyFunction/g)||[]).length === 0);       // no dangling ref
// every local $ref resolves against catalog.$defs
const refs = [...txt.matchAll(/"\$ref":\s*"#\/\$defs\/([^"]+)"/g)].map(m=>m[1]);
assert(refs.every(n => catalog.$defs[n]));
```

## 4. Part B — Renderer side

Goal: make the schema’s promises actually run — execute functions, dispatch events, write inputs back, and (critically) **re‑render** when state changes.

Context for this repo: components are built with a **binderless** implementation — for each component we read the A2UI props, resolve bindings ourselves, and hand clean props to the real React component. The wiring below lives in that implementation ([`src/pdsCatalog.tsx`](../client/src/pdsCatalog.tsx)) plus the app shell ([`src/App.tsx`](../client/src/App.tsx)).

### B1. Run the action — `functionCall` locally, `event` to the agent

```ts
function runAction(actionSpec, checks, context, dc) {
  // 1) sibling checks gate the action
  if (Array.isArray(checks)) {
    for (const chk of checks) {
      let ok = true; try { ok = !!dc.resolveDynamicValue(chk?.condition); } catch { ok = false; }
      if (!ok) { window.alert(chk?.message || "Validation failed"); return; }
    }
  }
  // 2) fire it
  if (actionSpec?.functionCall) {
    dc.resolveDynamicValue(actionSpec.functionCall);       // runs openUrl / setData / …
  } else if (actionSpec?.event) {
    context.dispatchAction(dc.resolveAction(actionSpec));   // resolves context paths, emits to the app
  }
}
```

**Why two paths?** The framework's `surface.dispatchAction` **only** emits `event` actions (to the app's action handler). It intentionally does **nothing** for `functionCall` — *"local functionCall actions are handled by the renderer."* So we run functions ourselves via `dc.resolveDynamicValue(functionCall)`, which invokes the registered function through the catalog's function invoker.

Attach it to the component's handler — click for most, close for dialogs:

```ts
const CLOSE_ACTION = new Set(["Modal", "Notification"]);
if (actionSpec) props[CLOSE_ACTION.has(name) ? "onClose" : "onClick"] =
  () => runAction(actionSpec, checksSpec, context, dc);
```

### B2. Handle **Action‑valued props** (e.g. `onClose`)

`Modal.onClose` is not the generic `action` prop — it's a prop whose *value* is an Action object. Passing that object straight to a React `onClose` (which wants a function) breaks it. Detect and wrap:

```ts
const isAction = (v) => isObject(v) && ("functionCall" in v || "event" in v);
// in the prop loop:
if (isAction(value)) { props[key] = () => runAction(value, null, context, dc); continue; }
```

### B3. Two‑way binding — **uncontrolled + write‑back**

When a state prop (`value`/`checked`) is a binding, render the control **uncontrolled** (`defaultValue`/`defaultChecked`) and write each change into the data model:

```ts
const TWO_WAY = {
  InputField: { prop: "value",   defaultProp: "defaultValue",   read: e => e?.target?.value },
  TextArea:   { prop: "value",   defaultProp: "defaultValue",   read: e => e?.target?.value },
  Checkbox:   { prop: "checked", defaultProp: "defaultChecked", read: e => e?.target?.checked },
  Toggle:     { prop: "checked", defaultProp: "defaultChecked", read: e => e?.target?.checked },
};
// in the prop loop, when the bound state prop is a DataBinding:
props[twoWay.defaultProp] = resolveValue(value, dc);
props.onChange = (arg) => dc.set(value.path, twoWay.read(arg));   // dc.set writes the model
```

> **Gotcha #5 — why *uncontrolled*.** See B5: binderless components don't re‑render on data changes. A *controlled* `value` bound to the model would therefore **freeze** (its prop never updates as you type). Uncontrolled lets the DOM own the text so typing is native, while `onChange` keeps the model current for events/validation to read. (If you also add B5 reactivity you *can* go controlled, but uncontrolled avoids cursor‑jump and is robust either way.)

Each component's exact `onChange` signature matters — read your DS types. Simple inputs give `(event)` → `event.target.value`; **group** controls (radio/checkbox groups) typically give `(value, event)` → the value is the *first arg*. Add a `read` accordingly per component.

### B4. Register renderer functions (`setData`, `toggleData`)

`openUrl` (and validation/logic/format helpers) ship with the base catalog. Add local **data‑model mutators** so a UI can drive its own state without an agent round‑trip:

```ts
const setDataFn = createFunctionImplementation(
  { name: "setData", returnType: "void", schema: z.object({ path: z.string(), value: z.any() }) },
  (args, ctx) => ctx.set(args.path, args.value)               // ctx is the DataContext
);
const toggleDataFn = createFunctionImplementation(
  { name: "toggleData", returnType: "void", schema: z.object({ path: z.string() }) },
  (args, ctx) => ctx.set(args.path, !ctx.resolveDynamicValue({ path: args.path }))
);
// merge into the catalog: [...basicCatalog.functions.values(), setDataFn, toggleDataFn]
```

**Why these are the DS's job:** the base catalog deliberately ships only `openUrl`. State mutation (open/close/toggle/tabs) is where your DS defines the local vocabulary. The function invoker validates `args` against the zod `schema` and passes the triggering component's **DataContext** as the 2nd arg — `ctx.set(path, value)` is your write primitive.

### B5. **Data‑model reactivity** — the piece that makes it visible

This is the subtle one. In this framework, a **binderless** component only re‑renders when it's **created/deleted** — *not* when the data model changes. So `setData` would update the model but the `Modal` bound to `opened` would never re‑render → it wouldn't open. Fix: subscribe each component to the data model and re‑render on any change.

```ts
const dataModel = dc.dataModel;
const store = React.useMemo(() => {
  let version = 0;
  return {
    subscribe: (cb) => { const s = dataModel.subscribe("/", () => { version++; cb(); }); return () => s.unsubscribe(); },
    getSnapshot: () => version,
  };
}, [dataModel]);
React.useSyncExternalStore(store.subscribe, store.getSnapshot);
```

**Why subscribe to `/`?** Every `set` notifies the changed path *and its ancestors up to the root*, so a single subscription to `/` catches all changes. This makes *all* one‑shot bindings live (modal open state, bound text, etc.). It's coarse (any change re‑renders every component) but correct and fine at typical surface sizes; optimize later by subscribing to specific paths if needed.

> **Gotcha #6 — reactivity is renderer‑specific.** If your DS uses the framework's **generic binder** (not binderless), reactivity is already handled for you and B5 is unnecessary. Check how your components render before adding this. The symptom of missing reactivity: "clicking updates state but nothing on screen changes," and "inputs won't type."

### B6. Give `event` actions somewhere to land

Events are emitted to the app's action handler (the 2nd arg of the message processor). In a real app this calls your agent; for a demo, make it observable:

```ts
new MessageProcessor([catalog], (action) => {
  console.log("[a2ui event]", action);        // { name, surfaceId, sourceComponentId, timestamp, context }
  // → send to your agent here
});
```

### Renderer side — the prop loop, assembled

Order inside the per‑component prop loop:
1. `action` → capture (wire to onClick/onClose after the loop).
2. `checks` → capture (passed to `runAction`).
3. `isAction(value)` → wrap as a handler (e.g. `onClose`).
4. `child` / `children` → child wiring (unchanged).
5. bound state prop (`TWO_WAY`) → uncontrolled + `onChange` write‑back.
6. everything else → `resolveValue` and pass through.
Plus, once per component: the B5 reactivity subscription.

## 5. The non‑obvious facts (cheat‑sheet)

| # | Fact | Consequence |
|---|---|---|
| 1 | `unevaluatedProperties: false` rejects undeclared props | Declare `action`/`checks` on the shared base, or agents emit invalid JSON |
| 2 | `action` on the base doesn't reach nested item `$defs` | Inject `action` into `ButtonGroupItem`‑style oneOf variants |
| 3 | `Action` has **no** `checks`; `checks` is a sibling (`Checkable`) | `{ checks:[…], action:{…} }`, never `{ action:{ checks } }` |
| 4 | Catalog refs point at an external spec URL nobody inlines | Vendor the common types into local `$defs` |
| 5 | The framework runs `event` but **not** `functionCall` | Renderer must execute functions itself |
| 6 | Binderless components don't re‑render on data change | Subscribe to `/` via `useSyncExternalStore`, or the UI looks frozen |
| 7 | `Modal.onClose` value is an Action object, not a function | Wrap Action‑valued props into handlers (`isAction`) |
| 8 | Controlled bound inputs freeze without reactivity | Render bound inputs uncontrolled + write‑back |

## 6. Replication checklist (any design system)

**Design‑system repo (catalog):**
- [ ] Add `action` (`$ref` A2UI `Action`) to the shared component base.
- [ ] Add `checks` (array of `CheckRule`) to the shared base — sibling of `action`.
- [ ] Convert `value`/`checked`/`opened` (and any controlled state) to `Dynamic*`.
- [ ] Convert close/dismiss handlers to `Action`; drop them from `required`.
- [ ] Inject `action` into interactive nested `$defs` (button groups, footers…).
- [ ] Vendor the A2UI common types into local `$defs`; make all refs `#/$defs/*`; strip `FunctionCall.oneOf` (or define `anyFunction`).
- [ ] Verify: 0 external refs, 0 dangling refs, every local `$ref` resolves.

**Renderer/app repo:**
- [ ] Wire the `action` prop → onClick (or onClose for dialogs), gated by `checks`.
- [ ] Wire Action‑valued props (`onClose`) → handlers via an `isAction` check.
- [ ] Run `functionCall` via the data context; dispatch `event` via the surface, resolving context paths first.
- [ ] Register your local functions (`setData`, `toggleData`, plus any DS‑specific ones); confirm `openUrl` is present.
- [ ] Two‑way bind inputs: uncontrolled + `onChange` → `dataContext.set(path, value)`. Handle per‑component `onChange` signatures (esp. group controls).
- [ ] Ensure reactivity: if binderless, subscribe to `/` and re‑render; if generic‑binder, it's automatic.
- [ ] Point the message processor's action handler at your agent (or log it).

**Prompt/agent side (if you generate A2UI with an LLM):**
- [ ] Teach the event‑vs‑function decision, the function vocabulary, two‑way binding, and `checks`‑as‑sibling. The schema alone can't convey the *decision* — the prompt must. (See `src/systemPrompt.js` → the `# Interactivity` section.)

## 7. How to test

- **openUrl:** a Button/TextLink with `action.functionCall` `openUrl` → opens the URL on click.
- **event:** a submit Button with `action.event` → the app's action handler receives `{ name, context }` with `context` paths resolved from the model.
- **two‑way:** an `InputField` with `value: { path }` (seeded in `updateDataModel`) → typing updates the model; the submit event carries what you typed.
- **modal:** seed `ui.open=false`; a button `setData /ui/open true`; a `Modal` with `opened: { path:"/ui/open" }` and `onClose` `setData /ui/open false` → opens and closes with no agent round‑trip.
