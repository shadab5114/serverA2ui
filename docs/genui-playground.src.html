Agentic Generative UI on the Verizon Design System

An agent composes UI on demand, and the Verizon design system is what makes that composition safe, on-brand and repeatable. This is the architecture that runs it: how a request becomes a screen, where the design system enters, and what keeps anything unapproved off the screen.

01 — Overall architecture

Four layers and one turn

One turn in five steps. Everything after this is the same turn with more detail.

The same turn, layer by layer. Each layer answers a different question: what the user sees, how it travels, who decides, and what constrains the decision. State cuts across all four. If a new feature doesn’t sit in exactly one layer, it isn’t scoped yet.

02 — Where the design system team’s work lands

One catalog, three jobs

This is the impact argument in one picture. The artifact the design system team already maintains feeds three different parts of the system. A component change reaches all three at once, instead of being re-implemented three times.

03 — How the backend decides

Reuse or create, and stay grounded either way

For every prompt and persona, the backend decides whether a curated template covers the request or whether it has to create new UI from the catalog. When it creates, it is creative in a place where it can be checked. The LLM proposes; the policy decides.

  1. Decide

    What’s needed, and does a template cover it? Returns a strategy, gaps and a reason.

  2. Policy

    Is this persona allowed that strategy? Plain code, not a prompt. Falls back if not.

  3. Ground

    Only when creating: RAG and MCP turn the gaps into a cited design brief.

  4. Build

    Fill a template, patch it, or compose from the catalog, following the brief.

  5. Verify

    Schema gate plus guideline gate. Repair, or ask the designer.

  6. Respond

    UI, plus the reason and sources for the trace panel.

One graph, persona as policy

Both personas run the same pipeline. personas.json decides what each may do, so curated customer flows can’t be rearranged by a prompt.

Creative in the brief, faithful in the build

Divergent thinking happens in the cited brief. The build follows it, and the guideline gate is what makes creative output safe to show.

Data never comes from the LLM

Prices and features come from data providers. If a request needs a field that doesn’t exist, the agent says so instead of inventing it.

04 — User flow

Two personas, one template library

The customer and the designer start from the same curated templates. The customer gets them exactly as designed. The designer can explore changes on top of them, grounded in the Verizon design system’s guidelines and checked by the same gates.

Both flows move along one dial: how much the agent decides.

PinnedTEMPLATE: curated layout, live data
ComposedADAPT · REFINE: patches on a curated template

What makes this more than UI that appears

UI that simply appears is indistinguishable from a designer with a good prompt. The evidence is in the trace panel: the agent choosing a curated template over inventing one, explaining why, consulting the Verizon design system’s guidelines, and being corrected by its gates.

That’s why the decision’s reason is sent to the client, why TOOL_CALL_* is a first-class event rather than a debug log, and why every grounding tool returns { answer, sources[] }. Making the grounding step visible is an architecture decision, not a UI one.
